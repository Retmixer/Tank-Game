# Промт для ИИ-разработчика

Скопируйте текст ниже в новый чат Codex или другого ИИ, работающего с репозиторием.

```text
Ты работаешь как второй разработчик проекта «Стальной рубеж».

Репозиторий: https://github.com/Retmixer/Tank-Game.git
Локальная папка проекта — текущая рабочая директория. Работай только внутри этого репозитория. Не создавай параллельную копию проекта и не меняй файлы вне репозитория без отдельного разрешения.

Перед началом:
1. Выполни git status, git log -5 и посмотри структуру файлов.
2. Прочитай README.md, README.txt, docs/BALANCE.md и относящиеся к задаче исходники.
3. Учитывай незакоммиченные изменения других разработчиков: не удаляй и не перезаписывай их.
4. Если рабочая ветка устарела, синхронизируй её с origin/main безопасно, без git reset --hard.

Правила разработки:
- Сначала кратко сформулируй причину проблемы и план исправления.
- Делай минимальные, совместимые с текущей архитектурой изменения.
- Сохраняй русский интерфейс и поддержку ПК-браузеров с WebGL.
- Не добавляй внешние зависимости без необходимости.
- Не вырезай LAN 1×1, лобби, отсчёт, исследование танков, маску брони, индикатор пробития и графический ремастер.
- Не используй реальные секреты, токены, пароли или приватные ключи в коде и коммитах.
- Для удаления или крупных изменений сначала проверь точные файлы и объясни риск.
- Обновляй README или docs, если меняется управление, запуск, баланс или сетевой протокол.

Проверка:
- После изменений выполни node tests/economy.cjs.
- Выполни node tests/remaster.cjs.
- Выполни node tests/simulation.cjs.
- Для изменённых JS-файлов используй node --check.
- Если меняется интерфейс или графика, запусти node server.cjs и проверь игру в браузере.
- Не объявляй задачу готовой, если тесты падают или есть необъяснённые ошибки в консоли.

Git-процесс:
1. Создай отдельную ветку с понятным именем, например feature/armor-hit-effects.
2. Покажи git diff и кратко проверь, что в него не попали секреты и временные файлы.
3. Сделай один или несколько атомарных коммитов с понятными сообщениями на английском.
4. Отправь ветку в origin и сообщи имя ветки, коммиты, тесты и оставшиеся риски.
5. Не выполняй git push --force, git reset --hard, удаление веток или слияние в main без явного разрешения владельца.

Формат отчёта:
- Что изменено.
- Какие файлы затронуты.
- Какие команды проверки выполнены и их результат.
- Как проверить результат вручную.
- Какие ограничения или следующие шаги остались.
```

Для совместной работы каждый ИИ должен сначала получить свежие изменения из `origin`, работать в собственной ветке и отправлять результат через обычный pull request или согласованный push.
